# 证书生命周期实验平台

本地的 X.509 证书签发、轮换、交叉签发与链验证实验平台。后端使用 Go 标准库
`crypto/x509` 真实生成 ECDSA P-256 证书与 CRL；页面为零依赖静态资源，直接由
Go 服务内嵌托管（不需要 Node 构建）。

## 运行

```bash
cd backend
go run ./cmd/certlab
# 打开 http://localhost:8080
```

服务启动时自动载入三组本地样例；页面上的“载入本地样例”可随时重置后重新载入。

## 验证规则

## 双重回看：事件时刻 × 获知截止

每次验证（一次历史调查）由两个独立时刻决定：

- **事件时刻 eventTime**：要研究的过去时刻。证书有效期、撤销生效时间都按这一
  时刻判断；
- **获知截止 knowledgeCutoff**：调查允许使用的材料的取得截止时刻。只有在此之
  前取得的证书、撤销记录、信任决定与 CRL 才参与判断——迟到、被更正或互相矛盾
  的材料各自带有生效时间与获知时间，并列展示，不会用今天的新材料覆盖过去已
  保存的研究。

两件事可能不同：撤销材料后来才收到，却说明证书更早已经失效。同一事件时刻可以
在取得新材料后建立新版本的调查，旧版本仍按当时知识重现（历史证据不可变）。

材料的时间模型：

- 证书有取得时间（learnedAt）；交叉签发的新证书不会出现在获知截止更早的调查中；
- 撤销是追加式记录（生效时间 + 获知时间）；“更正撤销日期”追加一条新记录，
  旧记录保留，截止时刻在更正之前的调查仍得到旧结论；“撤回撤销”同样只追加
  撤回记录，不会改写旧调查；撤销可登记为“现在获知、过去生效”的晚到材料；
- 根信任是事件日志，每条决定区分**生效时间**与**获知时间**：路径按“事件时刻
  生效、且获知截止前已获知”的决定判断。根先受信、事件随后发生、最后根停止
  受信时，用较晚获知截止复查该事件仍判为受信——停止受信只影响其生效时间
  之后的事件。信任变化也可以提前预约（现在获知、未来生效），生效前不改变
  当前受信根集合；
- CRL 的每次签发都追加到签发日志（ThisUpdate/NextUpdate 覆盖区间 + 获知时间，
  冻结于签发时刻）：CA 建链、撤销/撤回/更正、每次实时调取都会记录一条。历史核对
  按“获知截止前已获知、且覆盖区间包含事件时刻”的签发选取，条目只含当时已获知的
  撤销；改变查询截止点不会改写材料的生效、获知与覆盖时间。报告据此区分三种情况：
  当时已有覆盖事件的有效材料、材料后来才获知（获知时间晚于截止）、以及真实缺失
  （CA 不发布撤销资料）；缺少覆盖事件时期的撤销材料时结论保留为“尚缺依据”，
  不强行判定。

同一来源出现互相矛盾的材料（多条撤销记录、多条信任决定）时，报告采用“事件
时刻生效的最新决定 / 获知时间最新的撤销记录”，并在采用材料的时间依据中明确
写出存在冲突及采用依据，不会仅按最后写入悄悄覆盖。

每条路径与每份报告都带有“决定因素”分类（信任生效 / 撤销生效 / 证据缺失 /
期限 / 用途 / 签名 / 实验策略）。页面的“多获知截止对照”面板对同一事件时刻
用多个获知截止分别复查（每次复查生成新证据），对照表标出相邻结论的差异
来自信任生效、撤销生效还是证据缺失。

## 报告冻结与持久化

每份历史报告冻结当次可见的材料与策略：后续新增、修正或撤回材料只会产生新的
对照报告，旧结论不变。每次状态变化（包括每次验证追加的证据）都会把完整实验
状态——证书（含本地私钥）、信任日志、撤销记录与全部证据——原子写入快照文件
（默认 ./certlab-state.json，可用环境变量 CERTLAB_STATE 指定）。重新启动时
从快照恢复，页面继续展示原报告与材料版本；首次启动无快照时自动载入样例。

因此不同的路径得到不同的具体原因：某条路径在事件时刻有效但当时缺少必要证据
（尚缺依据），另一条资料完整却不符合那时的根要求（明确不合格），不会统一归为
失败。历史比较行会区分结论变化来自新增知识、事件时刻移动还是信任条件改变。
每条路径附带“采用材料的时间依据”（类型、生效时间、获知时间），每条证据可导出
JSON，导出结果逐路径携带实际采用材料的时间依据。

每次验证会枚举终端证书到自签根之间的全部候选密码学路径，并对每一条路径检查：

- 签名链完整且由 `x509.Certificate.Verify` 确认（单张证书签名正确不代表通过）；
- 链上每张证书的生效/失效期限；
- 终端证书 ExtKeyUsage 是否包含所选用途（serverAuth / clientAuth）；
- 末端必须是当前受信任的根锚点；
- 每个签发 CA 必须发布撤销资料；CRL 为实时生成，校验签名、时效与序列号。

结果会给出实际采用的路径；所有候选路径（采用与排除）都会展示，并区分三态：

- **采用 / 候选有效**：全部检查通过，其中按实验策略被选中的一条标记为“采用路径”；
- **明确不合格**：期限、撤销、用途、锚点、签名或 CRL 列名等确定性失败；
- **尚缺依据**：撤销资料缺失或尚未生效（迟到 CRL），无法确定撤销状态。

某条路径资料不全不影响其他完整路径独立判断；全部路径都缺依据时整体结论为
“尚缺依据”，保留不确定部分而不是强行判定失败。

## 实验策略（每次验证可指定）

验证表单可为单次实验指定：

- **允许的根**：只接受列出的根锚点，其他根的路径标记为“超出允许范围”；
- **根优先顺序**：多条有效路径时，采用根优先级最高的那一条；
- **必须具备完整撤销资料**：勾选后缺 CRL / 迟到 CRL 的路径直接判为不合格。

策略随证据一起保存；修改偏好后重新验证，历史比较会展示策略差异、采用路径
变化以及结论（通过 / 尚缺依据 / 失败）是否改变。

## 规则变化比较

历史面板中，每条证据会自动与同证书、同用途的上一条证据比较，展示规则版本、
结论、采用路径、信任根集合以及路径上每张证书状态（信任、期限、撤销、撤销资料）
的前后差异。旧证据始终保留当时的实验时钟与规则版本：过期中间证书、信任根更换
或撤销资料更新只追加新证据，不会改写历史判断，可随时展开旧证据回到当时的结论。

## 证据留存

每次“重新验证”都会生成一条不可变证据记录（自增 evidenceId、检查时间、规则版本、
全部候选路径明细）。信任根变化或 CRL 发布状态变化会使 rulesVersion 递增；新验证
只追加记录，不覆盖旧证据，历史按时间倒序展示。

## 本地样例

| 终端证书 | 场景 | 预期 |
| --- | --- | --- |
| leaf-ok | rootA→intermediateX 与 rootB→crossX（交叉签发同一中间密钥）两条信任路径 | 两条路径均有效，显示实际采用路径 |
| leaf-rotated | 同一中间 CA 轮换出的新一代终端证书（新密钥） | 独立验证，旧证书保留 |
| leaf-expired | rootC→expired-im（中间证书有效期为 -1 年，已过期） | 失败：期限不满足，即使签名全部正确 |
| leaf-nocrl | rootD→silent-im，该 CA 停止发布 CRL（撤销资料缺失） | 失败：revocation data missing |
| leaf-revoked | 已撤销终端证书，序列号出现在实时 CRL 中 | 失败：证书已撤销 / CRL 列名 |
| leaf-loop | imP 与 imQ 互相交叉签发成环，叶证书可经 rootE 或 rootF 到达 | 枚举不死循环，两条根路径均为候选 |
| leaf-late | tardy-im 的 CRL 生效时间在未来 30 分钟（迟到撤销材料） | 尚缺依据：撤销资料尚未生效 |

页面还可把 rootA 取消信任，演示根切换后 leaf-ok 自动改走 rootB→crossX 路径；
重新验证后历史中同时保留切换前、后两条证据。

## API 摘要

- GET /api/state：全部证书（不含私钥）、信任根、规则版本
- POST /api/roots、POST /api/intermediates（支持 crossSubjectId 交叉签发、负年数过期）
- POST /api/leaves、POST /api/leaves/rotate
- POST /api/certs/{id}/revoke、/trust、/crl
  （revoke 可带 revokedAt 登记晚到撤销材料；trust 可带 effectiveAt 预约未来
  生效的信任变化）
- POST /api/certs/{id}/retractrevoke：追加撤回记录（旧撤销记录保留）
- POST /api/certs/{id}/correctrevoke：追加更正的撤销生效日期（旧记录保留）
- POST /api/certs/{id}/crldelay：模拟迟到撤销材料（CRL ThisUpdate 延后 N 分钟）
- GET /api/crl/{id}：实时生成的 DER CRL
- POST /api/verify：执行验证并追加证据（可携带 eventTime / knowledgeCutoff（RFC3339，
  缺省为现在）与 policy：allowedRoots / preferredRoots / requireCrl）
- GET /api/history：不可变验证证据（新到旧）
- POST /api/samples、POST /api/reset
